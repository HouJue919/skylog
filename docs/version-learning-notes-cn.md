# SkyLog 版本学习笔记

这份文档记录 SkyLog 从 v0.1 到 v1.0 每个阶段做了什么、学到了什么、为什么重要。

## v0.1 静态 App 原型

### 做了什么

- 创建 Flutter 项目
- 把默认计数器 App 改成 SkyLog 首页
- 加入底部导航
- 创建 Home、Logs、Add、Map、Profile 五个主页面
- 使用静态数据展示 App 的基本结构

### 学到什么

- Dart 是编程语言，Flutter 是用 Dart 做 App 的框架
- `main()` 是 App 的入口
- Flutter 里的界面由 Widget 组成
- `StatelessWidget` 适合不需要变化的界面
- `StatefulWidget` 适合需要记住变化的界面
- `NavigationBar` 可以做底部导航
- `IndexedStack` 可以根据当前 tab 显示不同页面

### 为什么重要

v0.1 让 SkyLog 从想法变成了可以运行的 App 原型。虽然还不能保存真实数据，但已经能展示产品结构和主要页面。

## v0.2 可交互新增记录

### 做了什么

- 创建 `FlightRecord` 数据模型
- 用 `List<FlightRecord>` 保存多条飞行记录
- Add 页面可以创建一条新飞行记录
- 保存后自动跳到 Logs 页面
- Logs 页面显示新增的记录

### 学到什么

- 数据模型可以把相关信息组织在一起
- `List` 可以保存多条同类数据
- `TextEditingController` 可以读取输入框内容
- `setState()` 可以让界面根据数据变化重新显示
- 子页面可以通过 callback 把数据传回父页面

### 为什么重要

v0.2 让 SkyLog 从静态原型变成可交互原型。用户第一次可以输入数据，并看到 App 根据输入发生变化。

## v0.3 本地保存 MVP

### 做了什么

- 加入 `shared_preferences`
- 把飞行记录转成 JSON 保存到本地
- App 启动时读取本地记录
- 新增记录后重新打开 App，记录仍然存在
- 支持删除记录
- 添加 Logs 空状态

### 学到什么

- 本地存储可以让数据在 App 重启后保留
- JSON 是一种常见的数据交换和保存格式
- `toJson()` 可以把对象转成可保存的数据
- `fromJson()` 可以把保存的数据还原成对象
- `async` / `await` 用来处理需要等待的操作
- 删除数据后也要同步更新本地存储

### 为什么重要

v0.3 是 SkyLog 进入 MVP 的关键一步。数据不再只存在内存里，而是可以真正保存和恢复。

## v0.4 详情页和表单校验

### 做了什么

- Logs 里的记录可以点击进入详情页
- 详情页显示飞行数据、地图位置和总结
- Add 页面加入正式 `Form` 校验
- 标题、地点、时长为空时显示错误提示

### 学到什么

- `Navigator` 可以进行页面跳转
- `MaterialPageRoute` 可以打开新页面
- `Form` 和 `validator` 可以做输入校验
- 详情页可以让一条数据被完整查看
- 好的表单需要在用户出错时给清楚提示

### 为什么重要

v0.4 让 SkyLog 不只是列表，而是有完整记录详情。表单校验也让 App 更稳定、更像真实产品。

## v0.5 早期试用准备

### 做了什么

- Profile 页面显示版本信息
- 加入 `SkyLog v0.5` 和 `Early Tester Ready`
- 新增早期测试指南
- 保存记录后重置 Add 表单

### 学到什么

- App 不只需要功能，也需要让用户知道当前版本和状态
- 早期测试需要明确告诉用户应该测试什么
- 表单保存后重置可以减少连续输入时的混乱
- 项目文档也是产品开发的一部分

### 为什么重要

v0.5 让 SkyLog 更适合给熟人做小范围演示。它开始从“自己能用”走向“别人能理解”。

## v0.6 演示和反馈工具包

### 做了什么

- 创建 demo script
- 创建 feedback form
- 创建 portfolio checklist
- 更新 README，说明当前版本和运行方式

### 学到什么

- 用户测试需要有结构，而不是随便问“你觉得怎么样”
- Demo script 可以帮助演示更清楚
- Feedback form 可以收集更有用的反馈
- README 是别人理解项目的入口

### 为什么重要

v0.6 把项目从单纯开发，推进到用户研究和作品集准备。它对长期项目和大学申请都很有价值。

## v0.7 飞行日志搜索

### 做了什么

- Logs 页面加入真实搜索框
- 可以按标题、地点、日期、时长、无人机、天气和总结搜索
- 搜索无结果时显示提示
- 添加清除搜索按钮

### 学到什么

- `TextField` 可以接收用户输入
- `onChanged` 可以在输入变化时立刻响应
- `List.where()` 可以过滤列表
- `contains()` 可以判断字符串是否包含关键词
- 搜索功能本质上是“输入 -> 过滤数据 -> 更新界面”

### 为什么重要

SkyLog 的核心价值之一是让历史飞行可以被找回来。搜索让 Logs 页面从展示列表变成真正可用的记录工具。

## v0.8 编辑已有记录

### 做了什么

- 详情页加入 Edit / Save
- 可以修改已有飞行记录
- 保存后 Logs 页面同步更新
- 编辑后的数据继续保存在本地

### 学到什么

- CRUD 包括 Create、Read、Update、Delete
- `indexOf()` 可以找到要修改的数据
- 详情页可以有查看模式和编辑模式
- `late` 可以用于稍后初始化 controller
- 子页面可以提交修改，让父组件更新主数据列表

### 为什么重要

v0.8 完成了基础 CRUD。用户不仅能新增和删除，也能修正错误信息，这让 App 更接近真实可用。

## v0.9 Dashboard 和截图准备

### 做了什么

- Dashboard 统计改成根据真实记录计算
- 最近飞行和最近日志使用真实数据
- 新增中文截图计划

### 学到什么

- 首页统计应该来自真实数据，而不是固定假数字
- 可以从 List 中计算总数和总时长
- 展示型项目需要提前规划截图
- 作品集材料也是长期项目的一部分

### 为什么重要

v0.9 让 SkyLog 的展示更真实，也开始为作品集和项目展示做准备。

## v1.0 MVP 完成

### 做了什么

- 制定 v1.0 checklist
- 编写中文项目总结
- 添加完整 v1 workflow 测试
- 验证主流程：

```text
Add -> Save -> Search -> View Detail -> Edit -> Delete -> Export
```

### 学到什么

- 一个 MVP 需要有明确完成标准
- 自动测试可以验证核心流程
- 项目不是功能越多越好，而是核心流程稳定最重要
- 阶段性总结可以帮助自己真正理解项目

### 为什么重要

v1.0 是 SkyLog 的第一个完整里程碑。它证明这个项目已经从想法、原型、交互、本地保存，发展成了一个有核心闭环的本地优先飞行日志 MVP。

## v1.1 作品集展示打磨

### 做了什么

- 更新版本状态为 `SkyLog v1.1`
- 打磨 Home Dashboard 的展示效果
- 加入 Reset Demo Data，方便恢复干净演示数据
- 准备 portfolio 截图素材

### 学到什么

- 一个项目不只是“能跑”，还要能被别人快速理解
- Demo 数据需要稳定，否则展示时容易混乱
- 作品集需要清楚展示当前版本、功能和使用场景
- 自动测试可以帮助确认打磨 UI 时没有破坏核心功能

### 为什么重要

v1.1 让 SkyLog 更适合被展示。它开始从“开发项目”过渡到“可以讲给别人听的作品集项目”。

## v1.2 飞行前检查清单

### 做了什么

- 把占位 Map tab 换成 Pre-flight Checklist
- 加入 6 个飞行前安全检查项
- 勾选状态会保存在本地
- Home 页面显示检查进度
- 加入 Reset Checklist
- 添加自动测试，验证勾选和重置流程

### 学到什么

- `Set<int>` 适合保存“不重复的一组选中项目”
- checkbox 适合做二选一状态
- 本地存储不只可以保存飞行记录，也可以保存用户界面状态
- 产品功能应该围绕真实使用场景，而不是只加看起来酷的页面

### 为什么重要

v1.2 让 SkyLog 不只是在飞行后记录，也开始帮助飞行前准备。这个版本让项目更像真实无人机用户会需要的工具。

## v1.3 检查清单连接飞行记录

### 做了什么

- 给 `FlightRecord` 增加 checklist 完成度字段
- Add Flight 会把当前 checklist 完成情况保存进新记录
- 保存飞行后自动清空 checklist，准备下一次飞行
- Logs 卡片显示 `6/6 checks` 这种检查状态
- Detail 页面显示这次飞行前是否完成检查
- JSON 导出也包含 checklist 数据

### 学到什么

- 数据模型会随着产品功能成长
- 给旧数据加新字段时，要设置默认值，避免旧记录读取失败
- 一个功能如果能连接到核心数据，就比孤立页面更有价值
- 自动测试可以覆盖跨页面流程：Checklist -> Add -> Logs -> Detail

### 为什么重要

v1.3 把“飞行前准备”和“飞行后记录”连起来了。这个版本让 SkyLog 的使用流程更完整，也更容易向别人解释产品价值。

## v1.4 公开 Beta 稳定化

### 做了什么

- 更新版本状态为 `SkyLog v1.4`
- Profile 增加 About This Beta 说明
- Profile 增加 Privacy and Local Data 说明
- 解释 SkyLog 是记录工具，不是飞控 App 或官方安全系统
- 解释数据目前保存在本机，不会上传到云端
- 添加自动测试，确认两个说明弹窗可以打开

### 学到什么

- 准备公开测试不只是修 bug，也要减少用户误解
- 隐私和数据说明是产品可信度的一部分
- beta 版本要清楚说明“能做什么”和“不能做什么”
- 稳定化阶段可以先补齐说明、测试和边界，再继续加大功能

### 为什么重要

v1.4 让 SkyLog 更接近可以给别人试用的状态。别人打开 App 时，不只看到功能，也能理解这是一个本地优先的 beta 工具。

## v1.5 测试反馈工具包

### 做了什么

- 更新版本状态为 `SkyLog v1.5`
- Profile 增加 Copy Feedback Template
- 反馈模板会给 tester 一组具体问题
- 尝试把模板复制到剪贴板
- 即使剪贴板慢或失败，也会显示模板弹窗
- 更新 early tester guide
- 添加自动测试，确认反馈模板可以打开

### 学到什么

- beta 测试需要结构化反馈，而不是只问“感觉怎么样”
- App 可以帮助引导 tester 做更有价值的测试
- 剪贴板这类系统能力可能失败，所以 UI 要有 fallback
- 稳定化阶段关注的是“别人能不能顺利试用和反馈”

### 为什么重要

v1.5 让 SkyLog 更适合小范围外部试用。别人试完以后可以直接按模板反馈，你也更容易把反馈整理成下一轮迭代方向。

## v1.6 Beta 发布检查清单

### 做了什么

- 更新版本状态为 `SkyLog v1.6`
- Profile 增加 Beta Release Checklist
- 新增 `docs/beta-release-checklist.md`
- 检查清单覆盖核心流程、数据隐私、beta 边界和反馈流程
- 添加自动测试，确认 App 内检查清单可以打开

### 学到什么

- 发布前稳定化需要明确标准
- checklist 可以把“凭感觉准备发布”变成“按步骤确认”
- 文档和 App 内说明可以互相配合
- 固定网页上线前，要先确认 tester 不会误解数据、隐私和安全边界

### 为什么重要

v1.6 让 SkyLog 更接近固定网页部署前的状态。它没有急着加功能，而是建立了发布前的质量门槛。

## v1.7 已知限制和测试说明

### 做了什么

- 更新版本状态为 `SkyLog v1.7`
- Profile 增加 Tester Instructions
- 明确说明数据只保存在当前浏览器/设备
- 提醒 tester 使用样例或非敏感数据
- 说明 SkyLog 不是飞控 App，也不是官方安全系统
- 更新 early tester guide 和 beta release checklist
- 添加自动测试，确认测试说明弹窗可以打开

### 学到什么

- 对外测试前，限制说明和功能本身一样重要
- 用户需要知道“应该测什么”和“不应该怎么用”
- 本地存储的限制必须提前说清楚
- 稳定化阶段的重点是降低误解和支持成本

### 为什么重要

v1.7 让 SkyLog 更接近固定网页 beta。别人打开网页前后，都能清楚知道数据、隐私、安全边界和测试流程。

## v1.8 部署准备

### 做了什么

- 更新版本状态为 `SkyLog v1.8`
- Profile 增加 Deployment Readiness
- 新增 `docs/deployment-readiness.md`
- 记录固定网页前需要运行的命令：

```text
flutter analyze
flutter test
flutter build web
```

- 验证 Flutter Web 构建成功，生成 `app/build/web/`

### 学到什么

- 部署前不能只看 App 能不能在 VS Code 跑
- Web build 是固定网页上线前的重要检查
- `build/web` 是之后部署到 GitHub Pages 或 Netlify 的静态文件
- 上固定网页之前还要确认隐私说明、测试说明和反馈流程都清楚

### 为什么重要

v1.8 证明 SkyLog 已经具备生成网页版本的能力。它还没有正式部署，但已经完成部署前的技术检查。

## v1.9 固定网页 Beta 路线

### 做了什么

- 更新版本状态为 `SkyLog v1.9`
- Profile 增加 Fixed Web Beta Path
- 新增 `docs/fixed-web-beta-path.md`
- 新增 `.github/workflows/deploy-web.yml`
- 规划第一条固定测试链接使用 GitHub Pages
- 说明固定链接仍然只给 3-5 个可信 tester
- 添加自动测试，确认固定网页路线弹窗可以打开

### 学到什么

- 部署不是只把文件放到网上，还要有稳定、可重复的流程
- GitHub Actions 可以把 analyze、test、build、deploy 串起来
- Flutter Web 部署到子路径时，需要设置 `base-href`
- “固定网址”不等于“公开发布”，beta 分享范围仍然要控制

### 为什么重要

v1.9 把 SkyLog 从“可以构建网页”推进到“有固定网页 beta 路线”。这一步让之后真正部署到 GitHub Pages 更清楚，也更适合作为长期项目记录。

## v2.0 小范围 Beta 反馈

### 做了什么

- 更新版本状态为 `SkyLog v2.0`
- Profile 增加 Small Beta Feedback Plan
- 新增 `docs/small-beta-feedback-plan.md`
- 明确第一批 tester 不一定都要是无人机玩家
- 设计 3-5 人的小范围反馈流程
- 添加自动测试，确认反馈计划弹窗可以打开

### 学到什么

- 真实项目不是部署完就结束，而是进入反馈和迭代
- 第一批 tester 的重点是发现理解问题、流程问题和信任问题
- 普通用户也能测试可用性，不一定必须懂无人机
- 反馈要先记录，再决定下一版修什么

### 为什么重要

v2.0 让 SkyLog 从“可以被别人打开”进入“可以被别人有结构地测试”。这对长期项目和大学申请都重要，因为它证明项目有真实用户反馈和迭代过程。

SkyLog 到 v2.0 已经覆盖了一个真实 App 的基础开发流程：

- 产品想法
- 文档整理
- Flutter 页面
- 状态管理
- 表单
- 本地存储
- 搜索
- 详情页
- 编辑
- 删除
- JSON 导出
- 飞行前检查清单
- 数据模型升级
- beta 说明和隐私说明
- tester 反馈流程
- beta 发布检查流程
- 已知限制和测试说明
- Flutter Web 构建
- 固定网页 beta 路线
- GitHub Pages 部署 workflow
- 小范围 tester 反馈计划
- 自动测试
- 项目总结

下一阶段可以从三个方向选择：

- 开始 3-5 人小范围测试
- 根据反馈做 v2.1 修复
- 等稳定后再加入 CSV 导出或自定义 checklist
